# دليل Nexora PPE الصناعي

## حدود النظام

هذا الإصدار للمصانع ومواقع الإنشاء والورش الصناعية والمستودعات والمناطق الصناعية. لا توجد قوائم قطاعات أو اختيار موديل حسب الموقع؛ جميع المصادر تستخدم `ppe_unified_best.pt` نفسه. يظل اتخاذ القرار والتدخل من مسؤولية مشرف السلامة.

## 1. اعتماد ملف النموذج

1. احصل على الملف الأصلي المعتمد `ppe_unified_best.pt` وسجل اعتماد يتضمن SHA-256 ومصدر الملف وإصدار التصدير وقائمة الفئات وقياسات التقييم.
2. ضعه في `Model/ppe_unified_best.pt`، أو حدد مساراً مطلقاً بنفس اسم الملف في `PPE_MODEL_PATH`.
3. ثبّت البصمة في `PPE_MODEL_SHA256`. لا تُعد تسمية وزن آخر ولا تستخدم رابط تنزيل عام كبديل.
4. ثبّت `requirements.txt` للنشر، ثم شغّل:

   ```bash
   python -m app.model_check
   python -m app.model_check --smoke
   ```

5. الفحص الأول يتحقق من الملف والبصمة ومهمة الكشف وأسماء الفئات. `--smoke` ينفذ إطاراً فارغاً لاختبار توافق حزم التشغيل؛ **لا يقيس الدقة**.
6. افحص صوراً وفيديو ممثلة للموقع مع تعليم صحيح لكل قطعة ومخالفة، وحدد مقاييس القبول قبل تفعيل التنبيهات. تحقق خصوصاً من وجود زوجَي التصنيف الموجب والسالب لكل قاعدة ستستخدمها؛ الحد الأدنى الذي يتحقق منه المحمل هو Person والخوذة والسترة وأزواجهما السالبة.

الوزن المعتمد غير موجود ضمن التسليم الحالي. يبدأ فحص الملف قبل أي ترحيل قاعدة بيانات عند تشغيل API؛ عند غيابه لا ينشأ كاشف بديل ولا يبدأ الخادم.

## 2. إعداد الموقع والحسابات

- حساب البداية Admin يُنشأ عند فراغ جدول المستخدمين فقط، مع إلزام تغيير كلمة المرور.
- Admin ينشئ المصانع والمواقع: `factory`، `construction`، `workshop`، `warehouse`، `industrial`، ويضيف وصف الموقع.
- لا يمكن حذف موقع مرتبط بكاميرات؛ أعد ربطها أولاً.
- من صفحة المستخدمين يصدر Admin حسابات Supervisor أو Viewer بكلمات مؤقتة تُعرض مرة واحدة. إنشاء Admin إضافي محصور بالـCLI المحلي.
- Supervisor يدير المصادر والرفع ومعالجة الأحداث. Viewer يقرأ فقط، وتُفرض القيود في API أيضاً.
- لا تعِد ضبط متغير حساب البداية لاستعادة حساب قائم؛ استخدم `python -m app.cli reset-password --username site.admin`. إذا لم يبقَ Admin صالح، أنشئ Admin محلياً بالـCLI من جهاز إدارة موثوق.

## 3. اختيار مصدر الكاميرا وإعداده

1. حدّد `ALLOWED_RTSP_PREFIXES` لشبكات الكاميرات الفعلية. الأصل الدقيق مثل `rtsp://192.168.10.20:554` أفضل من نطاق واسع. يحظر السماح العام.
2. اختر النوع أولًا: `rtsp` يطابق `rtsp://` و`rtsps` يطابق `rtsps://`، ثم الاسم والموقع والرابط والمنفذ والقواعد. اذكر بروتوكول RTSPS ومنفذه في قائمة السماح إذا استُخدم. ضع اسم المستخدم وكلمة المرور في حقليهما؛ لا يقرأ النموذج المحفوظات السرية إلى المتصفح.
3. شغّل المصدر. لا يُعلن نجاح التشغيل قبل وصول إطار معالج حديث.
4. راقب البث والعدادات وحالة الاتصال. البيانات المنتهية الصلاحية لا تُعد مصدراً قيد التشغيل.
5. تعديل عنوان المصدر يوقف العامل؛ يلزم تشغيله من جديد. لا تُعرض بيانات الاعتماد أو المسار الكامل في استجابات قائمة الكاميرات.

`RTSP_OPEN_TIMEOUT_SECONDS=10` و`RTSP_READ_TIMEOUT_SECONDS=5` حدود فتح/قراءة OpenCV/FFMPEG. دعمها يعتمد على بناء OpenCV ومصدر البث؛ يجب اختباره على شبكة الموقع. تحرير المصدر متسلسل مع القراءة الأصلية لتجنّب تعارض الإلغاء مع OpenCV. لا يوجد اختبار كاميرا فعلية ضمن التحقق الحالي.

### مصفوفة الدعم والاختيار

| النوع | متى يُستخدم؟ | الدعم/الحدود |
| --- | --- | --- |
| `rtsp` | مصنع أو موقع إنتاج | موصى به؛ مسار الالتقاط السابق، بمهل 10s فتح و5s قراءة |
| `rtsps` | جهاز يدعم RTSP مشفرًا | دعم عبر مسار RTSP، ويلزم تحقق توافق الجهاز وTLS في الموقع |
| `http_mjpeg` | كاميرا توفر بث MJPEG مباشرًا | HTTP(S) multipart، Basic/Digest، مهلة و8MB لكل JPEG و24MP افتراضيًا؛ لا صفحة ويب أو snapshot |
| `hls` | رابط ويب `.m3u8` يوفره الجهاز/الوسيط | TS عادي 188-byte أو fMP4؛ حي/VOD؛ AES-128 identity؛ قائمة رئيسية حتى مستويَي تداخل؛ لا DRM/LL-HLS/renditions منفصلة |
| `file` | تجربة فيديو محفوظ | MP4/AVI داخل مجلد الخادم المسموح، مرة واحدة بالمعدل الأصلي |
| `usb` | تجربة جهاز محلي موصول بالخادم | dev فقط؛ تفعيل صريح وفهرس مسموح؛ لا وصول إلى كاميرا متصفح المستخدم |

### HTTP/MJPEG وHLS

لموقع يحتاج HTTP فقط يمكن توليد إعداد إنتاج مغلق لبقية الأنواع:

```bash
python scripts/setup_onprem.py --host nexora.site.lan --http-prefix http://192.168.10.30:8888/factory
```

يجوز تكرار `--http-prefix` أو جمعه مع `--rtsp-prefix`؛ يجب توفير قائمة شبكة فعلية واحدة على الأقل، ولا تُضف قائمة RTSP صورية لإكمال الإعداد. RTSP يظل التوصية الأولى إن وفره الجهاز.

- اضبط `ALLOWED_HTTP_CAMERA_PREFIXES`، وهي مغلقة افتراضيًا ومستقلة عن RTSP. مثال وسيط محلي: `http://192.168.10.30:8888/factory`. المنفذ والمسار جزء من السياسة؛ لا `*` ولا قبول أي URL عام.
- اختر النوع الموافق للرابط: MJPEG لا يقبل قوائم m3u8؛ وHLS لا يقبل RTSP. المصادقة Basic أو Digest اختيارية؛ يفضّل HTTPS. لا تضع كلمات مرور/توكنات في الاستعلامات، ولا تستخدم تحويلات URL؛ أدخل الرابط النهائي.
- يُفحص DNS عند كل مورد، وتُثبت وجهة الاتصال لمنع إعادة الربط مع إبقاء Host وTLS SNI الأصليين. لا بروكسي من متغيرات البيئة، ولا تحويلات أو نسخ مصادقة إلى أصل آخر؛ أضف نطاق CDN الضروري صراحةً إن احتاجه HLS. مصادر متعددة الأصول تتطلب المصادقة على الأصل الرئيسي فقط؛ مصدر فرعي يحتاج كلمة مرور مختلفة غير مدعوم، استخدم وسيطًا مقيدًا.
- تُجلب قوائم ومقاطع وخرائط تهيئة ومفاتيح HLS إلى مجلد مؤقت خاص بأسماء مولدة، ثم قائمة محلية مكتوبة ذريًا. يُفحص نوع الوسائط حتى بعد فك AES-128، وتُرفض القوائم المتنكرة والمراجع الخارجية لملفات داخل MP4.
- مفكك PyAV/FFmpeg يعمل في عملية مستقلة ببروتوكولي `file,crypto` فقط، لا يحصل على URL الشبكة أو كلمة المرور. يُنهى عند المهلة/الإيقاف وتُحذف الملفات المؤقتة؛ لا يستخدم أي نموذج ML آخر.
- حدود HLS: قائمة 256KB و1024 سطر، حتى 64 مقطعًا للقائمة، 32MB للمورد، مفتاح AES بطول16 بايت، مخزن128MB قابل للضبط ضمن16–512MB. القوائم الطويلة/العالية جدًا تُرفض بوضوح بدل ملء القرص. لقائمة VOD طويلة استخدم ملف فيديو معتمدًا أو وسيطًا بنافذة أقصر.
- الإخراج 960×540 مع حفظ النسبة وحتى `HLS_DECODE_FPS=5` افتراضيًا، ومعايرة الزمن حسب PTS حتى لا تُختصر مهلة ثبات PPE بفك VOD السريع. هذه ليست نتيجة قياس سرعة الكاشف أو دقته. HLS يضيف تأخير مقاطع؛ RTSP أنسب للمراقبة الصناعية منخفضة التأخير.
- مهل HTTP الافتراضية10s للفتح و10s للقراءة، وفتح HLS كله محدود بمجموعهما؛ يبدأ انتظار أول إطار بعد الفتح. يجب ضبطها حسب تأخير المقاطع الفعلي، لا تعطيلها.

### USB للتطوير فقط

```dotenv
APP_ENV=dev
ENABLE_USB_SOURCES=true
ALLOWED_USB_DEVICE_INDICES=0,1
```

اختر USB ثم فهرس الجهاز، دون URI أو مصادقة شبكة. يسمح النظام فقط بالقائمة المحددة؛ تستخدم القراءة عملية مستقلة حتى يمكن إيقاف سائق معلق. مهل الفتح5s والقراءة3s. لا يُسمح بالتفعيل في staging/prod، ويثبت Compose الإنتاجي التعطيل. لم يُختبر جهاز USB فعلي في هذا التسليم؛ اختبار العملية المعلقة يستخدم سائقًا اصطناعيًا صريحًا.

لوسيط HTTP على loopback أثناء التطوير فقط: يلزم `ALLOW_LOOPBACK_HTTP_SOURCES=true` **مع** إدخال الأصل والمنفذ والمسار في `ALLOWED_HTTP_CAMERA_PREFIXES`. كلا المفتاحين لا يجوز نقله إلى إنتاج.

### ONVIF والكاميرات الاقتصادية

`onvif_device_uri` عنوان تعريف اختياري فقط: HTTP(S) مسموح، بلا كلمة مرور أو query. لا ينفذ النظام WS-Discovery أو طلبات ONVIF، ولا يستخرج URI تلقائيًا. استخدم إعدادات الجهاز أو أداة ONVIF موثوقة للحصول على RTSP ثم سجله كمصدر RTSP.

بعض الأجهزة الرخيصة تحتاج تفعيل RTSP/ONVIF يدويًا، أو قد لا توفر إلا تطبيقًا سحابيًا. لا يكفي اسم ONVIF على العبوة لإثبات رابط فيديو صالح. يمكن استخدام mediamtx أو FFmpeg كوسيط محلي **إذا كان للجهاز مصدر قابل للقراءة**؛ لا يستطيع النظام اختراع بروتوكول مغلق. في mediamtx اختر `hlsVariant: mpegts` أو `fmp4` لا `lowLatency`، أو أعد نشر RTSP على منفذ مثل8554 واسم مسار ثابت، ثم اسمح بذلك الأصل/المنفذ فقط. ثبّت الوسيط وأمّنه بصورة مستقلة؛ لا ينشئه التطبيق أو ينزله تلقائيًا.

### حالات الاتصال وإعادة المحاولة

«جارٍ الاتصال»، «متصلة»، «إعادة اتصال»، «متوقفة»، «اكتمل»، «فشل الاتصال». بعد3 قراءات فاشلة تُجرى حتى محاولتَي إعادة فتح إجمالًا لكل تشغيل، بفاصل1s افتراضيًا، ثم يتوقف المصدر مع رسالة آمنة محفوظة. انقطاع مصدر لا يسقط مدير الكاميرات كله. تُمسح الإطارات والعدادات وبوابة أول إطار والثبات الزمني عند الانقطاع، وتصل حالة الانقطاع إلى WebSocket دون اختلاق أعداد صفرية. الملفات لا تُعاد تلقائيًا. الحالات الجارية في ذاكرة عملية المدير؛ الخطأ محفوظ في DB، وبعد إعادة تشغيل الخدمة يظهر المصدر غير النشط «متوقفًا» أو «فشل» إن كان له خطأ محفوظ.

## 4. الصور والفيديو

- الصور: JPEG/PNG، حتى 100 MB للملف، و24 مليون بكسل افتراضياً. تعرض الصورة المعلّمة والكشوف التي أعادها الكاشف فقط؛ لا تسجل حدث ثبات زمني لصورة منفردة.
- الفيديو: MP4/AVI، حتى 120 ثانية و100 MB افتراضياً. يُفحص فك الإطار والمدة والدقة، ويحفظ باسم UUID داخل `UPLOADS_DIR` المحصور داخل `ALLOWED_VIDEO_DIR`.
- المصدر المسجل يبدأ متوقفاً. شغّله من إدارة الكاميرات أو المراقبة؛ يُعالج مرة واحدة بمعدل إطاراته الأصلي، ثم يصبح غير نشط وتحرر موارده. لا توجد إعادة تشغيل دورية تلقائية.
- يُرفض مسار خارجي أو ملف غير مدعوم. لا يُستخدم اسم الملف المرفوع لبناء مسار التخزين.
- تنظيف الرفع الفاشل لا يحذف فيديو مصدر تم تثبيته بالفعل في قاعدة البيانات.
- راجع سياسة احتفاظ مساحة الفيديو يدوياً؛ حذف مصدر من الواجهة لا يمحو أرشيف الفيديو تلقائياً.

## 5. من الكشف إلى التنبيه

```text
RTSP / RTSPS / MJPEG / HLS / file / dev-only USB
  -> المصدر المقيد والمحدد زمنياً
  -> الكاشف المشترك الواحد (ثقة 0.50 افتراضياً)
  -> القواعد الصناعية المفعلة للمصدر
  -> ثبات التصنيف السالب + مهلة تكرار
  -> صورة دليل معلّمة + صف حدث + سجل تسليم
  -> اللوحة / البث / قائمة الأحداث / CSV
```

- افتراضياً يحتاج التصنيف السالب الصريح إلى 8 ثوانٍ متواصلة؛ الانقطاع أو إطار خالٍ منه يعيد الثبات.
- مهلة التكرار 60 ثانية لكل كاميرا/قاعدة، لا لكل هوية عامل. لا يوجد تتبع هوية أو استنتاج امتثال من غياب كشف موجب.
- معالجة حدث توثق مراجعته فقط؛ ليست إثبات إزالة الخطر أو تعديل معدات العامل.
- إحصائيات 24 ساعة و7 أيام محسوبة في SQL من السجل الكامل، وليست جمع الصفحة الظاهرة. فلاتر الموقع والكاميرا والحالة والنوع والتاريخ مشتركة بين القائمة والتصدير.
- التواريخ مخزنة UTC، وتعرضها الواجهة بوضوح. تتبع الانقطاع وإعادة الاتصال؛ قراءة `/health` وحدها لا تكفي لإثبات عمل الكاميرا أو جودة النموذج.
- ضبّط التنبيهات الاختيارية عبر SMTP أو Webhook فقط عند الحاجة، واختبر التسليم داخل الموقع. الصورة قد تتضمن أفراداً؛ طبق الموافقة وسياسة الاحتفاظ وأقل صلاحية.

## 6. الترقية والرجوع

1. أوقف المصادر والكتابة، وخذ نسخة من قاعدة البيانات والأدلة والفيديو وإعدادات التثبيت والوزن المعتمد وبصمته.
2. اختبر استعادة نسخة منفصلة قبل الترقية الفعلية.
3. الترحيل `20261024ind` يزيل المصادر/الأحداث غير المدعومة، يوقف المصادر الباقية، يطبّع الأدوار ويعطّل الحسابات غير المدعومة، يُبطل كل الجلسات ويُجبر تغيير كلمات المرور، ويضيف Sites وCamera.site_id ويحذف حقول النطاق السابقة.
4. الترحيل الإضافي `20261024src` يضيف `device_index/auth_mode/onvif_device_uri/last_error` ويصحح نوع RTSPS القديم، مع الحفاظ على المصادر والقواعد والمواقع والأحداث. اختبارات SQLite تؤكد ترقية متكررة غير مدمرة من `20261024ind`.
5. تبقى بصمة سجل التدقيق الأساسية، لكن تزال بيانات النطاق السابقة من التفاصيل.
6. الترحيل غير قابل للعكس؛ الاستعادة من نسخة ما قبل الترقية هي مسار الرجوع، وليست `alembic downgrade`.
7. صور الأدلة القديمة خارج SQL لا تُمحى بترحيل الصفوف. راجعها واعزل/احذف غير المطلوب وفق سياسة الموقع، أو ابدأ بمجلد أدلة صناعي نظيف مع الاحتفاظ بأرشيف الاستعادة المقيد.

يمكن تشغيل الترحيل يدوياً، بعد النسخ الاحتياطي، بـ`python scripts/alembic_cli.py upgrade head`. هذا أمر ترحيل صريح منفصل عن بوابة الوزن في بدء الخادم.

## 7. بوابة التجربة الميدانية

لا تعتمد منصة تشغيلية نهائية قبل اكتمال الآتي:

- الملف المعتمد، البصمة، توافق الفئات والبيئة وحزم ML.
- تقييم مستقل على نهار/ليل/حجب/ازدحام ومسافات وزوايا الكاميرات الفعلية، لكل قاعدة.
- ضبط الثقة والثبات والمهلة وفق نتائج موثقة؛ لا توجد أرقام دقة أو FPS معتمدة في هذا التسليم.
- اختبار انقطاع/عودة RTSP، انتهاء الفيديو، إبطال الجلسة، فشل التسليم ونفاد التخزين.
- اختبار حمل الجهاز وعدد الكاميرات وزمن الإطار، ثم النسخ والاستعادة وخطة الاستجابة للإنذار.
- اختبار PostgreSQL/Compose وشبكة الموقع وشهادة TLS. تحقق SQL Server، إن استُخدم، في بيئته وبسائق ODBC المناسب؛ الاختبارات المحلية للترحيل تستخدم SQLite.

التطبيق يستخدم مدير كاميرات داخل عملية واحدة؛ شغّل Uvicorn **بعامل واحد**. زيادة عدد العمليات تكرر الالتقاط والعدادات ولا توفر تنسيقاً موزعاً.
