# Nexora On-Premise: التشغيل والأمان

هذا الدليل خاص بتثبيت مستقل داخل شبكة العميل. التطبيق لا يحتاج حسابات Cloud أو خدمة دفع أو اتصالاً بخادم Nexora المركزي؛ كل تثبيت له قاعدة بياناته وملفاته الخاصة. **التحقق من استلام الكاش وإصدار بيانات الدخول عملية يدوية خارج البرنامج**، ولا يوجد تسجيل ذاتي.

> وجود التطبيق داخل الموقع لا يكفي وحده للأمان. يجب تقييد الشبكة، تركيب شهادة HTTPS موثوقة على أجهزة المستخدمين، وتحديث النظام ونسخ قواعد البيانات احتياطيًا.

## 1. إنشاء إعداد إنتاج آمن

على جهاز الخادم من مجلد المشروع:

```bash
python scripts/setup_onprem.py \
  --host nexora.customer.lan \
  --rtsp-prefix rtsp://192.168.10. \
  --rtsp-prefix rtsp://10.10.0.
# If the defaults overlap a customer/VPN route, append:
# --edge-subnet 10.253.240.0/24 --data-subnet 10.253.241.0/24
```

- أدخل اسم DNS الذي سيستخدمه العميل، واجعل DNS الداخلي يشير إلى عنوان الخادم.
- استبدل نطاقات RTSP بأضيق شبكات كاميرات/VLAN فعلية ممكنة؛ لا تضع `*` ولا نطاق شبكة المكتب كلها.
- ينشئ الأمر `.env` بأسرار عشوائية مستقلة لهذا الموقع، وصلاحية `0600`، وكلمة مرور مؤقتة قوية لحساب `admin`.
- لا ترسل ملف `.env` للعميل ولا تضعه في Git. احتفظ بنسخة تشغيل آمنة وخزّن مفتاح النسخ الاحتياطي منفصلًا عن ملفات النسخ.
- راجع `.env` يدويًا قبل التشغيل. أضف prefix لكل شبكة كاميرات فعلية، ولا توسّع القائمة إلا عند الضرورة.

تحتاج الحزمة إلى Docker Compose plugin v2.33 أو أحدث (لتحديد مسار الخروج صراحةً). ثم شغّلها:

```bash
docker compose up --build -d
```

يفتح المستخدمون `https://nexora.customer.lan`. يستخدم Caddy افتراضيًا CA داخليًا دون الاعتماد على Cloud أو ACME. بعد تشغيل Caddy، استخرج **الشهادة العامة فقط** وثبّتها في مخزن الثقة على الأجهزة المعتمدة:

```bash
mkdir -m 700 -p certs
docker compose cp proxy:/data/caddy/pki/authorities/local/root.crt certs/nexora-root.crt
```

وزّع `certs/nexora-root.crt` عبر إدارة أجهزة العميل الآمنة أو استبدل إعداد TLS بشهادة المؤسسة الموثوقة. لا تنسخ أو توزّع `root.key` مطلقًا، ولا تتجاهل تحذير الشهادة في المتصفح. يحتوي volume `caddy_data` على مفتاح CA الخاص؛ احمِ volume واحتفظ به ضمن خطة استعادة مقيدة.

شبكتا Docker `edge` و`data` داخليتان: Caddy على `edge` يصل إلى API فقط، وقاعدة البيانات على `data` لا يصل إليها إلا API. شبكة `cameras` غير داخلية وموصولة بحاوية API فقط لكي تصل إلى كاميرات العميل؛ **هذه الشبكة تسمح بمسار egress من المضيف**. لا يستدعي Nexora خدمة Cloud افتراضيًا، لكن يجب على مسؤول الشبكة ضبط firewall على المضيف لتمرير وجهات/منافذ الكاميرات المصرح بها فقط ومنع الوصول العام، وعدم اعتبار allowlist التطبيق بديلًا عن firewall. تكاملات SMTP/webhook تبقى معطلة ما لم تُفعّل صراحةً وتُضاف وجهاتها المعتمدة إلى سياسة firewall. `TRUSTED_PROXIES` وUvicorn يثقان بعنوان Caddy المحدد `/32` فقط. تستخدم الإعدادات الافتراضية `172.30.100.0/24` و`172.30.101.0/24`؛ تحقّق من عدم تداخلهما مع شبكات العميل/VPN قبل التثبيت، واستخدم `--edge-subnet` و`--data-subnet` عند الحاجة. لا يعرّض Compose منفذ API أو PostgreSQL مباشرة؛ قيّد 80/443 حسب سياسة الموقع، ولا تفتح PostgreSQL أو `8000` على الإنترنت.

## 2. تهيئة الكاميرات ومجلد الفيديو

- RTSP/HTTP: كل URI يتحقق من scheme وhostname والمنفذ ثم يطابق `ALLOWED_RTSP_PREFIXES`. عند عدم تحديد منفذ في allowlist تُقبل المنافذ القياسية فقط (RTSP 554، RTSPS 322، HTTP 80، HTTPS 443)؛ اسمح بمنفذ مخصص بكتابته صراحة في الـ prefix. القائمة الفارغة ترفض الكاميرات الشبكية. عناوين loopback وlink-local وmetadata محظورة حتى لو أضيفت بالخطأ.
- ملفات الفيديو: `/var/nexora/videos` هو mount للقراءة فقط إلى مجلد `./videos` على المضيف. المسارات النسبية تُفسّر داخله، ويُمنع الخروج منه أو اتباع symlink إلى خارجه. ضع فقط مقاطع التشغيل المقصودة في هذا المجلد.
- بيانات RTSP لا تُعاد للواجهة ولا تُكتب في سجلات المصدر؛ قاعدة البيانات ما زالت تخزن URI التشغيل، لذا احمِ ملفات قاعدة البيانات والخادم نفسه.

## 3. إصدار مستخدم بعد استلام الدفع

لا يوجد endpoint تسجيل عام، ولا يثبت Nexora حصول الدفع. لإصدار حساب يدويًا بعد الدفع، ومن جهاز الخادم:

```bash
docker compose exec app python -m app.cli create-user \
  --username customer1 \
  --sector construction \
  --role viewer
```

يعرض الأمر كلمة مرور مؤقتة **مرة واحدة فقط**، ويلزم المستخدم بتغييرها أول مرة. سلّمها عبر قناة خاصة ومعتمدة لدى العميل، ولا تضعها في البريد الجماعي أو التذاكر.

الأدوار:

- `viewer`: قراءة الكاميرات/البث والمخالفات والتصدير فقط.
- `operator`: صلاحيات المشغل؛ إضافة/تعديل/حذف/تشغيل الكاميرات ومعالجة المخالفات، ضمن القطاع المخصص.
- `admin`: إدارة المستخدمين والصلاحيات وعمليات المشغل ضمن القطاع. لا يمكن إنشاء Admin جديد من API؛ يُنشأ أو يُرقّى من CLI محليًا فقط.

أوامر إدارة الحسابات:

```bash
docker compose exec app python -m app.cli list-users
docker compose exec app python -m app.cli reset-password --username customer1
docker compose exec app python -m app.cli disable-user --username customer1
```

يمكن لمدير التثبيت إصدار حسابات `viewer` أو `operator` من API الإدارة. لو شرط العمل أن إصدار كل حساب جديد يبقى بيد البائع فقط، **لا تسلّم بيانات `admin` للعميل**؛ احتفظ بها لمسؤول التثبيت واستخدم CLI بعد تأكيد الدفع. أي شخص يملك صلاحية root/إدارة الخادم يستطيع تجاوز ضوابط التطبيق محليًا بطبيعة التشغيل on-prem.

تُفرض كلمة مرور لا تقل عن 12 حرفًا وثلاثة أنواع أحرف، ولا تتضمن اسم المستخدم؛ تُخزّن PBKDF2-SHA256 عند 600,000 دورة على الأقل. تغيير كلمة المرور أو تعطيل الحساب يرفع `token_version` ويلغي الجلسات السابقة، كما تعيد اتصالات MJPEG/WebSocket فحص حالة الجلسة كل 5 ثوانٍ كحد أقصى. تسجيل الخروج يلغي جلسات الحساب كلها. لا توجد خدمة استعادة Cloud؛ يحتفظ مسؤول الموقع بإجراءات إعادة تعيين محلية آمنة.

## 4. جلسات المتصفح والشبكة

- Access cookie: `HttpOnly`, `Secure`, `SameSite=Strict`, host-only، مدة 240 دقيقة افتراضيًا.
- Media cookie منفصل بنوع JWT مستقل ومدته 10 دقائق، يُجدّد عبر API مصادق عليه. لا يوجد token في `localStorage` أو query string للـ MJPEG/WebSocket/frames.
- لا يصدر endpoint login قيمة JWT في JSON. بعد انتهاء access token يلزم تسجيل الدخول مجددًا؛ لا يوجد refresh token دائم.
- CORS الإنتاجي يرفض `*` ويقبل HTTPS origin المحدد فقط. `ALLOWED_HOSTS` مضبوط أيضًا على hostname المعتمد.
- سياسة HTTPS تُفرض في وضع الإنتاج، وCaddy يرسل HSTS ورؤوس منع framing وMIME sniffing. لا تشغّل واجهة الإنتاج عبر HTTP مباشر.
- `/health` يجيب `{"status":"ok"}` فقط. `/metrics` وبيانات الإدارة تتطلب حسابًا مناسبًا.
- حد تسجيل الدخول 5 محاولات/IP/دقيقة، وقفل مؤقت للحساب بعد 5 إخفاقات خلال نافذة القفل. تُسجّل محاولات كلمة المرور المرفوضة حتى حد IP مع hash للمعرّفات؛ طلبات 429 الزائدة لا تُسجّل فرديًا لتجنب إغراق السجلات/قاعدة البيانات. حد IP محلي للعملية ومحدود الذاكرة، ولذلك يشغّل Compose worker واحدًا كما يتطلب CameraManager أيضًا؛ يمكن إضافة حد إضافي على reverse proxy/firewall عند الحاجة.
- احتفظ بنسخة من إعداد proxy/trusted proxy للشبكة الصحيحة إذا غيّرت شبكة Docker. لا تثق في `X-Forwarded-For` من عميل مباشر.

## 5. النسخ الاحتياطي المشفر والاستعادة

إنشاء نسخة PostgreSQL مشفرة بـ AES-256-GCM، دون كتابة dump غير مشفر على المضيف:

```bash
scripts/backup_postgres.sh
```

الملفات الناتجة في `backups/*.nxb` بصلاحية محلية مقيدة. مفتاح التشفير موجود في `.env`؛ احتفظ بنسخة منه في مخزن أسرار منفصل وآمن. فقدان المفتاح يعني تعذر استعادة النسخ.

مثال استعادة من ملف النسخة المنقول إلى المضيف (اختبر أولًا على قاعدة تجريبية). انسخ الملف المشفر إلى volume، أوقف API، ثم استخدم حاوية تشغيل لمهمة فك التشفير إلى pipe فقط؛ لا يُكتب dump مفكوك على المضيف:

```bash
archive=nexora-postgres-<timestamp>.nxb
docker compose cp "backups/$archive" "app:/var/nexora/backups/$archive"
docker compose exec -T -u 0 app chown 1000:1000 "/var/nexora/backups/$archive"
docker compose stop app
docker compose run --rm --no-deps -T app python -m app.backup decrypt \
  --input "/var/nexora/backups/$archive" --stdout \
  | docker compose exec -T db sh -c \
    'pg_restore --clean --if-exists --no-owner --no-acl -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
docker compose start app
```

لا تنقل dump غير مشفر ولا ملف `.env` في القناة نفسها مع النسخة الاحتياطية. اختبر الاستعادة دوريًا على نسخة منفصلة.

## 6. العزل والتشغيل متعدد المواقع

التصميم الحالي **تثبيت واحد وقاعدة بيانات واحدة لكل عميل**؛ لا تشارك قاعدة البيانات أو volume أو أسرار التثبيت بين العملاء. عزل القطاعات والأدوار داخل التثبيت ليس بديلًا عن عزل العملاء على مستوى قاعدة بيانات مستقلة.

للبايلوت، استخدم شبكة داخلية أو VPN، جدارًا ناريًا، وموظفًا واحدًا لإدارة الأسرار والحسابات. أوقف SQL echo/debug، ولا ترفع `.env` أو النسخ الاحتياطية أو ملفات الفيديو إلى Git.

## 7. تحديثات الاعتماديات والنسخ

لا يحتاج التطبيق العامل إلى Cloud أو خدمة دفع أو اتصال بخادم مركزي. وصول الشبكة الصادر موجود فقط لأن API يجب أن يتصل بكاميرات العميل؛ اترك إعدادات SMTP/webhook فارغة، وقيّد egress على المضيف إلى نطاقات الكاميرات ومنافذها المعتمدة. إذا احتاج الموقع تكاملًا داخليًا محددًا، أضف وجهته إلى قائمة firewall بعد مراجعتها، ولا تفتح خروجًا عامًا ولا تضع أسرارًا لخدمات شخصية/عامة مثل Gmail أو Slack.

قبل كل إصدار وعلى جهاز تحديث معتمد، افحص الاعتماديات ثم ابنِ/سلّم صورًا معتمدة إلى الموقع:

```bash
python3 -m venv /tmp/nexora-audit-venv
/tmp/nexora-audit-venv/bin/pip install pip-audit
/tmp/nexora-audit-venv/bin/pip-audit -r requirements/prod.txt
cd frontend
npm ci
npm audit
```

حدّث `requirements` و`package-lock.json` إلى إصدارات مصححة، وأعد الاختبارات والبناء ومراجعة release notes قبل استبدال الصور. افحص كذلك صور Docker وحزم نظام التشغيل بماسح مؤسسي محدث؛ سجل نتائج الفحص وتاريخها مع كل إصدار. لا تثبّت تحديثات عشوائية مباشرة على موقع العميل، ولا تفتح اتصالًا outbound دائمًا لكي يعمل التطبيق.

## 8. حدود الأمان الحالية

هذا hardening دفاعي واختبارات آلية، وليس شهادة امتثال أو تقرير اختبار اختراق. لم تُفعّل 2FA بعد؛ أضفها قبل نشر إدارة حساسة على شبكة غير موثوقة. قبل فتح الخدمة للإنترنت العام، يلزم مراجعة مستقلة تشمل TLS/headers، حدود reverse proxy، استعادة النسخ، اختبار صلاحيات القطاعات، وفحص الاعتماديات دوريًا. الأفضل أن يبقى التثبيت على شبكة العميل خلف firewall/VPN.
